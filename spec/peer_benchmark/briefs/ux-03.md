# ux-03 — Glossary tooltips for icons and relics (data-driven, reuse the card keyword tooltip stack)

## Header
- Owner, playtest 7 (2026-10-15): relics "use a lot of iconography. And that iconography doesn't have any explaining
  tooltip" — both when choosing a relic and when looking at owned relics. More generally, icons that carry meaning must
  explain themselves on hover/focus.
- The director will rewrite all definitions later (ux-02 audit → rewrite). This unit builds the mechanism and seeds the
  data **verbatim from existing definitions**; it invents no player-facing text.
- Base: `codex/peer-benchmark`. Owned files: new `data/glossary.json`, new `scripts/glossary.gd` (loader + lookup),
  `scripts/card_keyword_rules.gd` (only to read keyword definitions from the glossary instead of code, keeping the
  rendered text identical), `scripts/card_focus_tooltip_stack.gd` (generalize for non-card owners), the relic choice
  and owned-relic display scripts (find them; plumbing for hover/focus only), the inline icon token renderer in
  `scripts/action_icon_library.gd` only if hover hit-testing needs it, new `tests/glossary_*`, new
  `tests/glossary_tooltip_probe.gd` + contract. Do not edit `scripts/run_scene.gd` beyond the minimum plumbing (list
  every line you touch there).
- Rules: use the existing tooltip components (`ui_tooltip_panel.gd`, `card_focus_tooltip_stack.gd`) and the visual design
  system; no new tooltip look. UI identity lint must not rise (`python3 tests/test_ui_identity_lint.py`). Mouse hover,
  keyboard focus and controller focus must all open the same tooltips. Windows typed-array rule.

## Change
1. **Glossary data** `data/glossary.json`: one entry per concept (keywords, statuses, elements, damage types, resources,
   intent icons, relic icon tokens): `id`, `name`, `icon` (path or icon-library id), `definition` (BBCode allowed),
   `aliases`. Seed every definition verbatim from where the game defines it today (keyword rules, status tooltips,
   intent tooltips, icon library labels). Where an icon has no definition anywhere, create the entry with
   `"definition": "TODO_DESIGN_GLOSSARY_<id>"` and list it in the result — never write a definition yourself.
2. **Card keywords read from the glossary**: the card keyword tooltip stack renders exactly as today (pixel-identical
   capture of a focused card with keywords before/after), but its text comes from `data/glossary.json`.
3. **Relics get the same stack**: hovering/focusing a relic in the relic choice screen and in the owned-relic display
   shows the relic's name and description panel plus one glossary panel per distinct icon token / keyword used in its
   description (same order rule as cards: first appearance order; at most 4 glossary panels, then "+N more" is NOT
   added — show all if ≤ 6, otherwise the first 6). Same placement rules as the card stack (never off-screen; flips side
   near edges).
4. **Inline icon hover**: any inline icon token rendered inside a tooltip or rules text that is itself hoverable gets
   the glossary panel on hover/focus where the existing UI already supports nested hover; elsewhere, the containing
   item's stack (item 3) already lists it.
5. **Coverage test**: every icon token and keyword used anywhere in card, relic and status text resolves to a glossary
   entry (TODO_DESIGN entries allowed but counted and printed).

## Proof
- Tests: glossary coverage, card keyword pixel-identity (before/after capture equality), UI identity lint, full suite.
- Windowed (list the commands; the director runs them): the glossary tooltip probe capturing at 1920×1080 a relic choice
  with a hovered relic, the owned relic display with a hovered relic, a focused card with keywords (before/after equal),
  keyboard-focus versions of the first two.

## Out of scope
Rewriting text (ux-04), the chronicle (chr-02), any new tooltip styling.
