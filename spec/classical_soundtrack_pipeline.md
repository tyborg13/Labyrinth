# Classical soundtrack pipeline

This is the production path for adapting public-domain classical compositions into Escape the Umbra's restrained 16-bit dark-fantasy style. It keeps source rights, musical transformations, procedural instrumentation, audition versions, and game promotion auditable and reproducible.

## Quick start

Use Python 3.12 and the pinned packages:

```bash
python3.12 -m venv .venv-classical-soundtrack
.venv-classical-soundtrack/bin/pip install -r tools/classical_soundtrack_requirements.txt
.venv-classical-soundtrack/bin/python tools/classical_soundtrack.py doctor
.venv-classical-soundtrack/bin/python tools/classical_soundtrack.py generate-bank
.venv-classical-soundtrack/bin/python tools/classical_soundtrack.py scaffold \
  --track-id beethoven_op67_movement_ii \
  --title "Symphony No. 5, Movement II" \
  --composer "Ludwig van Beethoven"
```

The scaffold is intentionally locked. Complete `LICENSE_SOURCE.md`, save the original source byte-for-byte under `source/`, record its SHA-256 in `track.json`, and set `source.rights_status` to `cleared` only after the evidence is unambiguous. Rendering refuses uncleared or drifted sources.

## Source gate

Use sources in this order:

1. OpenScore CC0 MusicXML, MuseScore, or MIDI.
2. Another reputable CC0 or explicitly public-domain machine-readable transcription.
3. A public-domain IMSLP edition followed by a reproducible transcription.

Never use a modern copyrighted arrangement, commercial MIDI, audio recording, SoundFont, sample pack, ripped game/console audio, ROM content, or generated-model audio as the musical or instrumental source. If rights are ambiguous, stop and find a different source. An IMSLP public-domain edition is useful as a visual cross-check even when OpenScore supplies the machine-readable source.

`LICENSE_SOURCE.md` and the `source` object in `track.json` must agree on the composition, composer, immutable URL, source format, license status/evidence, retrieval date, local filename, and SHA-256. Keep the original file unchanged.

## Track layout and versioning

New work lives under `output/classical_soundtracks/<track_id>/`:

```text
LICENSE_SOURCE.md
README.md
track.json
source/                         immutable downloads and license evidence
normalized/
  full_score.musicxml
  full_score.mid
  parts/                        separate original instrumental parts
scripts/
  build_arrangement.py          score-specific deterministic transformation
versions/
  v01/
    arrangement.mid
    preview.ogg
    preview.flac
    preview.render.json
    VERIFICATION.json
    ARRANGEMENT_NOTES.md
```

Create `v02`, `v03`, and so on for revisions. Never overwrite an audition version the user may want to revisit. The score-specific build script is the source of truth for selections, cuts/repeats, transposition, voice allocation, gates, velocities, tempo, and added percussion; do not hand-edit its generated MIDI.

Preserve the original parts separately whenever the source is an ensemble score. The first version should stay faithful: preserve harmony and recognizable thematic/counterpoint material, retain upper-voice action, favor a strong but not masking cello/low register, limit the practical melodic texture to roughly four to six voices, and keep percussion supportive.

`tools/classical_soundtrack_pipeline/normalization.py` provides `load_score` and `write_normalized_score`. The score-specific build selects the intended movement first, then the helper writes normalized full-score MusicXML/MIDI plus separately named MusicXML/MIDI parts. An OpenScore file that embeds several movements in one continuous score still needs explicit, work-specific movement-boundary logic; document and test those boundaries against the public-domain reference edition.

Every `ARRANGEMENT_NOTES.md` must explain:

- selected measures or time windows and their new order;
- retained, omitted, repeated, or octave-doubled events;
- pitch/harmony changes, including an explicit statement when there are none;
- velocity, gate, balance, pan, timbre, echo, percussion, and loop treatment;
- how the version differs from the previous audition.

## Shared procedural bank

`assets/audio/instruments/classical_dark_fantasy_v1/` is generated by `tools/classical_soundtrack.py generate-bank`. The eight WAVs are mathematical synthesis only: five low-rate looped bowed timbres and three restrained one-shot percussion sounds. The manifest includes the exact synthesis parameters and sample hashes.

Treat the bank id as a versioned interface. Mix changes belong in a track config. A synthesis change that alters a WAV hash requires a new bank directory/version so existing approved renders remain reproducible.

The Schubert v03 config at `output/schubert_d810_movement_ii_retro_poc/driving_tactical_loop.track.json` is the style reference. Its balance keeps both violin lines legible, the cello and octave shadow dominant, the viola intact, and the funeral pulse quieter and drier than the strings.

## Render and verification

After the score-specific script creates a versioned MIDI and its SHA-256 is recorded:

```bash
.venv-classical-soundtrack/bin/python tools/classical_soundtrack.py render --config output/classical_soundtracks/<track_id>/track.json
.venv-classical-soundtrack/bin/python tools/classical_soundtrack.py verify \
  --config output/classical_soundtracks/<track_id>/track.json \
  --report output/classical_soundtracks/<track_id>/versions/v01/VERIFICATION.json
```

The renderer supports a fixed, flattened performance tempo. Expressive source tempo changes should be deliberately flattened by the versioned arrangement script and documented. It uses the shared 16 kHz bank, per-track gain/pan/release/vibrato, a small reconstruction filter, restrained three-tap circular dark echo on strings, dry filtered percussion, gentle saturation, peak normalization, equal-power loop crossfade, lossless FLAC, and Ogg Vorbis. Vorbis is only the delivery codec; it adds no musical or sample rights. New scaffolds may use `vorbis_encoder: auto` while auditioning, but an approved config should freeze `native` or `libvorbis`; the render report records the implementation and FFmpeg version, and expected hashes expose toolchain drift.

Verification rechecks source clearance and hash, every bank sample hash, MIDI hash and named-track note counts, strict FFmpeg decode, duration, peak, silence, and optional expected Ogg/FLAC hashes. Set `expected_outputs` after approving a render so later rebuilds expose drift.

Render experimental settings into a temporary `--output-dir` first. Promote only an explicitly approved version:

```bash
.venv-classical-soundtrack/bin/python tools/classical_soundtrack.py promote \
  --config output/classical_soundtracks/<track_id>/track.json \
  --asset-path assets/audio/music/<game_track_name>.ogg
```

Promotion verifies first and refuses to replace a different asset. Then add or update the provenance note beside the game asset, wire the intended context in `MusicLibrary`, keep boss routing unchanged unless requested, run focused music routing/import tests, and provide a playable inspection fixture.

## Audition gate

Give the user the MIDI, Ogg preview, a short transformation summary, and two or three concrete next directions. Do not iterate again until the user gives taste feedback. After approval, freeze expected hashes, verify, peer-review the exact commit, and follow the repository publication workflow.
